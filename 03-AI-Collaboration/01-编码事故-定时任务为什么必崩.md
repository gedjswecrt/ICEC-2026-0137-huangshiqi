# 01 · 编码事故：同一份代码，我跑正常、定时任务必崩

- **时间**：2026-11-15 01:54
- **所属**：阶段二 · 项目四「每日校园早报」
- **版本**：v0.1 → v0.2（本次修复触发升版）
- **证据**：`02-20Days-Challenge/process_logs/telemetry_20261115.jsonl`（连续 3 条同名报错）

## 问题

程序在终端手动运行一切正常；交给 Windows 计划任务后，每次运行都崩在同一行：

```
schedule: 'utf-8' codec can't decode byte 0xd0 in position 0: invalid continuation byte
```

`0xd0` 是关键线索——UTF-8 编码里不会以这个字节开头，它更像是 GBK 汉字的高位字节。

## 我的提问

> 同一个脚本，我在终端跑没事，计划任务跑就报编码错误，为什么？是不是它找错文件了？

## AI 给的方案

先区分「代码错」还是「环境错」，不急着改代码：

1. 用 `xxd` 直接看 `data/schedule.csv` 的字节头 → 确认文件实际是 **GBK（ANSI）**
2. 解释运行差异：手动运行时读到的是另一个已变更的版本，定时任务读到的是磁盘上那份 GBK 文件
3. 修复：读取函数按 `utf-8-sig → utf-8 → gbk` 依次尝试，取第一个成功者

## 我的判断

采纳多编码兜底，但追加一条要求：**日志必须记录实际使用了哪种编码**。否则以后出问题无从追溯。

同时确认了根因责任：这个文件是我自己用记事本改课表时保存的，Windows 记事本默认存 ANSI 而不是 UTF-8——不是程序的锅，但程序应该兼容它。

## 验证

修复后计划任务再次触发，日志记录 `v0.2 · 0 报错`，课程段落正常输出。

日志里 v0.1 的 3 条编码报错与 v0.2 的 0 报错在同一份文件内前后相邻，改动效果可直接对照：

| 版本 | 记录数 | 情况 |
|---|---|---|
| v0.1 | 7 | 2 次天气超时 + 3 次编码错误 |
| v0.2 | 2 | 全部 0 报错，其中 1 条为 07:30 全自动运行 |

## 复盘

- 「手动可以、自动不行」几乎总意味着**运行环境差异**：工作目录、环境变量、权限、编码
- 编码问题不靠猜，`xxd` 看一眼字节头，30 秒出结论
- 这次修复的依据全部来自日志（日志字段设计见 06），所以报错一条都没删
