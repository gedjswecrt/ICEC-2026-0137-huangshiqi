## 日志字段说明（telemetry_*.jsonl，每天一行）

```json
{
  "run_id":      "20261115-011949",        // 脱敏时间戳
  "version":     "v0.1",                    // 程序版本，便于追溯迭代
  "steps":       [每个步骤的 ok/detail/耗时ms],
  "api_calls":   1,                         // 外部 API 调用频次
  "errors":      [],                        // 报错清单（自动捕获）
  "total_cost_ms": 4135,                    // 全程耗时
  "success":     true
}
```

## 迭代纪律（20 分的关键）

每次迭代必须：① 先在日志里找到依据（报错/慢/用户反馈）→ ② 改代码 → ③ git commit（message 写明依据）→ ④ 把 diff 截图存到 `iterations/`。**没有日志依据的改动等于白改。**

## 设计说明：DDL 为什么是"公共"的

早报发给全班同学看，因此 `data/ddl.csv` 只录**全班相关**的事项（作业、考试、班务、考核截止），不放个人私事。
天气与课程对同班同学天然通用。

**已知局限（记入反馈问卷）**：每个人的私人 DDL 不同，早报无法覆盖。
→ 问卷中将询问"DDL 板块对你有用吗、希望怎么改"，根据反馈在迭代 3 中改进
（候选方案：公共/个人两栏、同学提交个人 DDL 的共享表格、或仅保留考试与作业类提醒）。

## 风险与对策

- **电脑当天没开机 / 断网** → 日志会记一条 failed run（这也是真实日志）；补跑一次并注明。宁可日志里有失败记录，也不要伪造"全绿"
- **天气 API 再挂** → 已做双源冗余（wttr.in + open-meteo）
- **同学不用** → 早报直接发群里，零操作成本；反馈问卷只要求"这几天看了几天、哪里有用"
