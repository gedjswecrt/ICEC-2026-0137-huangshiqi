# 迭代 6：v0.6 → v0.7（2026-11-19）

## 改动依据（用户反馈驱动，第 4 批用户 U08）

**用户反馈 U08（刘绍君，2026-11-19）**，截图见 `screenshots/feedback_U08_刘绍君_20261119.png`：

> 信息齐全；建议"加个降温提醒：降温了多穿衣服、小心着凉"

这是 8 位用户里**最后一条尚未落实的功能建议**（U04 的错题本/周总结、自动更新链接已明确不做或暂缓；U07 为纯好评无建议）。本轮只做这一件事，不动配色、不动排版、不动已有板块。

### 为什么不是"每天都写一句注意保暖"

早报每期已经有天气一行 + 3 条生活贴士。如果再加一句固定不变的"注意保暖"，就会变成每天都出现、看完就忘的废话——这恰恰是 U01/U02 当初批评过的"只有学业提醒、缺少生活内容"的反面：**内容不在多，在于出现得对**。

所以这一版的判定是：**只有真的降温才出现，平时整块不渲染**。

## 改动内容

### 1. 天气接口顺带取回今明两日的最高/最低气温

两个数据源本来就返回预报，只是此前只取了"当前天气"就丢掉了：

| 数据源 | 取温度的字段 |
|---|---|
| wttr.in（主源） | `weather[0].mintempC / maxtempC`（今天）、`weather[1].*`（明天） |
| open-meteo（备源） | 追加 `daily=temperature_2m_max,temperature_2m_min&forecast_days=2` |

**没有新增任何接口调用**，只是把已有响应里被忽略的字段读出来。运行耗时不变（实测 3256ms，与 v0.6 的 1470ms 差异来自网络波动，不是新增请求）。

取温度时每个字段都单独做 try/异常兜底，任一字段缺失就返回 `None`，**绝不因为预报字段缺失让早报生成失败**。

### 2. 降温判定：阈值 4°C，两条线任一成立

```python
COOL_DROP_C = 4
# 最低气温：明天最低比今天最低低 >= 4°C → 早晚明显更冷
# 最高气温：明天最高比今天最高低 >= 4°C → 白天也整体转凉
```

为什么是 4°C：深圳秋冬日常温差 1~3°C 属于正常波动，提醒了也没人当回事；4°C 以上才有"该翻出外套"的实际意义。这条线写成了常量，改一个数字就能调，不用翻代码。

触发时的文案（实际运行输出）：

> 🧥 明天最低比今天低 5°C，记得添件衣服。

一句话里带齐**明天多少度、降了多少度、该做什么**，不用读者自己算。

### 3. 不触发时整块不渲染

```python
cool_html = f'<p class="cool-tip">🧥 {cool_msg}</p>' if cool_msg else ""
```

没降温 → 空字符串 → 页面上连这个 `<p>` 都不存在，不是隐藏、不是空白占位。

### 3b. 但"明天几度"要常驻显示（补做）

第一版做完后有一个隐患：**不降温的日子里，早报上完全看不到这个功能的痕迹**。同学会以为没做，评审也无从判断这个改动是否存在——一个"只在特定天气下才现身"的功能，等于把可验证性交给了天气。

所以天气那一行改成两段：

```
阴，20°C，湿度55%，风速14km/h  · 明天 13~19°C
```

- **`· 明天 13~19°C`** —— 灰色小字，**每天都显示**。不降温的月份里它依然有用（知道明天穿什么），也让人看出这个板块确实有数据在算
- **蓝色提示块** —— **仅降温时出现**，是"提醒"本身

这样两个目标同时满足：功能始终可见、噪音只在该出现时出现。两种渲染结果对比：

| 场景 | 天气行 | 蓝色提示块 |
|---|---|---|
| 明天 19~25°C（今天 20~26°C，只差 1°C） | 晴，26°C… **· 明天 19~25°C** | 无 |
| 明天 13~21°C（今天 18~24°C，降 5°C） | 阴，20°C… **· 明天 13~21°C** | 🧥 明天最低比今天低 5°C，记得添件衣服。 |

### 4. 判定过程写进遥测日志

新增第 7 步「降温判定」，无论触发与否都记录：

```
降温判定 -> 触发：明天最低比今天低 5°C，记得添件衣服。（今最低18°C → 明最低13°C）
降温判定 -> 未触发（今最低20°C / 明最低19°C，降幅需≥4°C）
```

**理由**：如果不记，事后无法回答"11-19 那天为什么没弹降温提醒"——是没降温，还是程序坏了？把判断依据留在日志里，问题可以自查。

### 5. 顺带修一个显示问题：城市名是英文

天气卡片标题此前显示"今日天气（**Shenzhen**）"，因为 `CITY_NAME` 同时被用于查询接口和页面显示。v0.7 把它拆成两个：

- `CITY_NAME = "Shenzhen"` —— 传给 wttr.in，必须是英文
- `CITY_CN = "深圳"` —— 页面上显示

一份中文早报里冒出一个英文地名，属于明显的粗糙处，顺手改掉，不改任何逻辑。

## 验证

### 一、降温判定逻辑：8 个边界用例

把 `cool_alert()` 单独拿出来跑，覆盖"该提醒"和"不该提醒"两侧：

| # | 场景 | 今天/明天 | 期望 | 实际 |
|---|---|---|---|---|
| 1 | 最低降 8°C、最高降 9°C | 17/24 → 9/15 | 提醒 | ✅ 明天最高比今天低 9°C |
| 2 | 只差 1°C | 17/24 → 16/23 | 不提醒 | ✅ 不提醒 |
| 3 | 最低刚好降 4°C | 20/25 → 16/24 | 提醒 | ✅ 明天最低比今天低 4°C |
| 4 | 最低降 3°C（差一点） | 20/25 → 17/24 | 不提醒 | ✅ 不提醒 |
| 5 | 只有最高降 4°C | 25/30 → 24/26 | 提醒 | ✅ 明天最高比今天低 4°C |
| 6 | 温度字段缺失 | None | 不提醒 | ✅ 不提醒 |
| 7 | 反而升温 | 10/15 → 12/18 | 不提醒 | ✅ 不提醒 |
| 8 | 天气接口整体失败 | None | 不提醒 | ✅ 不提醒 |

**8/8 通过**。其中第 4、6、8 条是关键：差一点不提醒、数据缺失不提醒、接口挂了也不提醒——都不能因为判定模块而让早报出错。

### 四、留一份实例存档：`output/示例_降温提醒_v0.7.html`

## 复盘

1. **"不做"和"做"都要有判据**。上一轮把 U08 的建议记为待办时，写的是"只在真降温时出现"。这一轮把它变成了 `COOL_DROP_C = 4` 这个具体数字——**"看情况"不是设计，"4°C"才是**。阈值公开写在代码和文档里，别人可以质疑、可以改。
2. **最省力的功能往往是"重新读一遍已有的数据"**。天气接口从一开始就返回了预报，只是前六版都只取"当前天气"。这次没有新增请求、没有新增依赖、没有增加失败点，只是把已经付过费的响应多读了两个字段。
3. **降级要降到"不出错"，不是降到"出错"**。判定模块的 8 个用例里，3 个是异常场景（字段缺失、接口失败），期望值都是"不提醒"而不是"报错"。一个锦上添花的小功能，绝不能成为主流程的新故障点。
4. **日志的粒度决定复盘能力**。如果只记录"提醒了/没提醒"，事后无法区分"没降温"和"判定写错了"。把今天最低、明天最低、阈值三个数一起写进日志，一个 grep 就能定位。
5. **克制依然有效**。这一版总共改了约 60 行，其中判定逻辑不到 25 行。剩下一半是兜底、日志和注释。**功能本体的代码量应该小于让它不出事的代码量**——这是这几轮下来最稳的一条经验。
