# 迭代 5：v0.5 → v0.6（2026-11-18）

## 改动依据（用户反馈驱动，第 3 批用户 U06）

**用户反馈 U06（曾淑婷，2026-11-18 09:18 / 09:30 两段对话）**，截图见 `screenshots/feedback_U06_曾淑婷_20261118.png`：

> "建议就是……课程状态是生成时所固定，然后我希望在打开了网页就获取实时状态（因为班级情况）

> 但现在这个我记得他每天早上要生成一次，那网上获取的话，到中午或者下午的时候，他的上课状态就会发生变化
> 所以能够打开网页的时候，就是获取到实时状态会更好看一点"

**这条反馈点出了一个此前被忽略的真实缺陷**：v0.4 加入的"未开始/进行中/已结束"标签，是在**早报生成那一刻**算好后写死在 HTML 里的。而早报的实际使用方式是"早上生成 → 发到班级群 → 同学在不同时间打开"：

| 同学打开时间 | v0.5 显示 | 实际 |
|---|---|---|
| 早上 7:40 | 未开始（第 1 节） | 未开始 ✓ |
| 中午 12:00 | **未开始（第 1 节）** | 已结束 ❌ |
| 晚上 20:00 | **未开始（第 1 节）** | 已结束 ❌ |

也就是说，**除了 7:30 前后打开的人，全班看到的都是过期状态**。这个缺陷是"静态文件 + 多人异步查看"这一使用场景的必然产物，单靠每天多跑几次程序解决不了（总不能每小时手动生成一次发群里）。

## 改动内容

### 1. 课表状态标签改为浏览器端实时计算（核心）

- 每节课的起止时间写进 `data-start` / `data-end` 属性，标签初始为"未开始"
- 页面内嵌一段 JavaScript：**按访问者设备上的当前时间**计算状态，打开即刷新
- `setInterval(refresh, 60000)`：页面停留时**每分钟自动重算**，挂着不会过期
- 判断规则与 Python 端一致：`now < start` → 未开始 / `start ≤ now ≤ end` → 进行中 / `now > end` → 已结束

关键取舍：**没有引入任何外部依赖、没有联网请求**。早报依然是"单个 HTML 文件，发出去双击就开"，只是多了一段内嵌脚本。这也符合项目一贯的降级思路——即使浏览器禁用了 JS，网页上仍有"未开始"的初始标签，页面不会白屏。

### 2.「今日一句话」同步实时化

原来这句话也是生成时写死的（"下一节《智能视觉》8:40 开始"），下午打开同样过期。现在拆成两段：

- **课程部分**（前半句）→ 交给 JS 按打开时刻重算，逻辑与 Python 端一一对应
- **DDL 部分**（后半句）→ 沿用生成时的结论，通过 `data-tail` 属性传给脚本

这样"正在上什么"随打开时间变化，"最紧的是什么"保持稳定，两者不会互相干扰。

### 3. 页脚增加"阅读时间"

`生成时间 07:30:05 · 阅读于 20:35 · 早报机器人 v0.6`

这一行解决了另一个隐性困惑：同学看到早报时，无法分辨"这是什么时候的数据"。现在生成时间与阅读时间并列，一眼可见。

## 复盘

1. **最好的反馈来自真实使用场景**：U04/U05 提的是"我想看到什么"，U06 提的是"这个东西在班里用起来会怎样"——后者暴露的问题更致命（几乎全班看到的状态都是错的），也更难靠自己想到。三位用户分三批、三种视角，说明分批采集的设计是对的。
2. **静态文件不等于不能实时**：把"时间判断"从生成端搬到浏览端，一行 JS 就解决了"一份文件要服务一整天"的矛盾。这类改动价值高但成本低，属于典型的好迭代。
3. **一条反馈顺带修了三个地方**：标签、今日一句话、页脚阅读时间。它们本质是同一个问题（页面不知道"现在几点"）在不同位置的表现，找到根因比逐处打补丁更省力。
4. **克制**：这个机会本可以顺带引入网页托管（让链接永久有效，U04 也提过），但这会牵扯发布渠道和访问权限，超出本轮范围。一次只解决一类问题，留待后续评估。

### U08 建议的处理结论：**不做为独立功能，改为文案层小改（v0.7 候选）**

理由：
1. **技术上不需要新数据源**。现有天气接口（wttr.in 主源 + open-meteo 备源）已经返回当日最高/最低气温与体感温度，只要把"今天 17°C / 明天 9°C"这类**相邻两天温差**算出来，就能判断是否降温。不必新增接口、不必增加运行耗时。
2. **但"提醒"要克制**。早报每期已经有天气一行 + 每日贴士，如果再插一句"多穿衣服"，容易变成堆砌。更合适的做法是**只在真的降温时出现**（例如次日最低气温比今日低 5°C 以上），平时不显示——这符合项目一贯的"不啰嗦"原则。
3. **本轮不实现**。v0.6 刚于今日 07:30 自动上线，还没经过完整的班级使用验证；按"一天一版"的节奏，改动应在 11-19 晚开发验证、11-20 07:30 起生效，届时视时间安排决定是否落地。**在此明确记下：这是待办，不是已实现**，避免后续文档把 U08 的描述误当成已完成的特性。

补充说明：U07 的反馈没有可执行项，但它从"用得久了"的角度验证了产品方向——这属于口碑型反馈，不产生代码改动，也不应算作"建议未采纳"。8 位用户中，只有 U04（错题本/周总结、自动更新链接）和 U08（降温提醒）的建议尚未落地，且都已在文档中写明原因或计划。
